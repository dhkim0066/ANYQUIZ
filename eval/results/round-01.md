#### 03에서 따로 확인한 네 가지

**1. 5번(순서)·6번(삽입)이 schema.md 규약대로 담겼는가 → 담겼다. 단 렌더러가 삽입 보기를 잘못 출력한다.**

| | 규약 | 원본 분석 | 생성물 |
| :- | :- | :- | :- |
| order `passage` | 주어진 글, 그다음 (A)(B)(C)를 문제지 순서대로 | 지킴 | 지킴 |
| order `options` | 순서 조합 5개 | `(A)-(C)-(B)` 등 5개 | 같은 5개 조합 |
| order `answer` | 조합 인덱스 | 2 (③) | 3 (④ `(C)-(A)-(B)`) |
| insertion `passage` | 주어진 문장 맨 앞, 그다음 `( ① )`~`( ⑤ )` 박힌 본문 | 지킴 | 지킴 |
| insertion `options` | 위치 번호만 | `["①"…"⑤"]` | `["①"…"⑤"]` |
| insertion `distractor_notes` | 오답 위치마다 왜 어긋나는지 | 4개, 지시어 근거 | 4개, 지시어·대조 근거 |
| `passage_words` | 주어진 글·문장 포함 | 172 / 179 | 162 / 180 |

- 규약에 없어 추측한 것: 주어진 글과 단락 사이 구분자(빈 줄 + `(A) ` 접두로 처리), 순서 조합의 구분 기호(원본은 전각 `－`, 규약 예시와 산출물은 `-`).
- **렌더 결함:** 규약대로 담으면 `render_md.py`가 6번 아래에 `① ①` `② ②` … `⑤ ⑤` 목록을 출력한다. 원본에는 없는 줄이다. 또 주어진 글·문장이 인용 상자·굵게 없이 일반 문단으로 나온다.
- `passage_words`: 6번의 실제 영어 단어는 원본 155, 생성 약 163. 180은 위치 표시 15토큰과 각주를 포함한 값이다. 검증기가 공백 분리로 세기 때문에 이렇게 적어야 통과한다.

**2. 7·8번 분류 → `reading/blank-inference`** (원본 분석·생성물 모두).

에이전트는 이 분류를 추측 목록에 올리지 않았다(망설임 없이 결정). 반면 01(9~12번)과 02(7~8번)는 `cloze/single-blank`로 분류하면서 두 에이전트 모두 "경계가 불분명해 원본 영역 제목을 보고 정했다"고 보고했다. 세 장의 차이는 지문 길이(48~86단어 vs 152~156단어)와 영역 제목("빈칸"·"Fill in the Blank" vs "빈칸 추론")뿐이고, 보기는 세 장 모두 구(phrase)다. **분류가 맞게 나왔지만 규칙이 아니라 영역 제목에 기대고 있다.**

**3. 2·3·7·8번 생성물의 보기가 영어인가 → 네 문항 모두 영어.** 1·4번은 원본처럼 한국어.

단, 스킬에 보기 언어 규칙이 없다. 에이전트는 "문항별로 원본을 따랐다"고 추측 목록에 적었다. 스키마에 보기 언어를 담는 필드가 없고 `--compare`도 검사하지 않으므로, **다음 실행에서 한국어 보기로 나와도 잡히지 않는다.**

**4. 4번(안내문 불일치) 보기 다섯 개가 서로 다른 문장에 대응하는가 → 대응한다.**

| 보기 | 대응 문장 (지문 10문장 중) | 판정 |
| :- | :- | :- |
| ① 중학생과 고등학생이 참가할 수 있다 | 1번째 | 일치 |
| ② 디자인을 세 점까지 제출할 수 있다 | 2번째 (up to two designs) | **불일치 (정답)** |
| ③ 양식은 안내 데스크에서 받을 수 있다 | 3번째 | 일치 |
| ④ 우편으로 보낸 작품은 접수되지 않는다 | 5번째 | 일치 |
| ⑤ 수상과 관계없이 모든 출품작이 전시된다 | 10번째 | 일치 |

다섯 보기가 서로 다른 문장을 가리키고, 지문 등장 순서를 따르며, 불일치 보기는 숫자 하나만 바꿨다. question-types.md detail 규칙 1·2·3을 모두 지켰다.

## 결정 필요

1. **작성 규칙 검사를 원본 분석에도 적용할 것인가.** 02 원본의 2번(정답 14단어, 나머지 최대 9)과 4번(정답 6단어, 나머지 최소 9)이 "정답만 길거나 짧음"에 걸린다. 원본은 고칠 수 없는 기준 데이터다. 제안: `validate_schema.py`에 원본용 모드를 두어 스키마만 검사하고 작성 규칙은 생성물에만 적용.
2. **원본 분석에 생성용 필수 필드를 요구할 것인가.** `distractor_notes`, 단어집 `example`·`pos`는 원본에 없어서 세 에이전트 모두 지어 넣었다(03은 예문 누락으로 31건 실패 후 채움). 분석 JSON에 생성기 판단이 섞이고, 3단계의 `NN.expected.json`에도 같은 문제가 생긴다.
3. **cloze와 reading/blank-inference의 경계.** 지금은 원본 영역 제목에 기댄다. 단어 수나 보기 형태(단어 vs 구)로 기준을 정해야 한다. 01·02의 빈칸 문항은 구 보기라서 single-blank 규칙("보기는 같은 품사", "2~3문장")과 이미 맞지 않는다.
4. **보기 언어를 스키마에 담을 것인가.** 03처럼 발문 한국어 + 보기 영어 혼합이 수능형의 기본이다. 지금은 우연히 맞았다.
5. **"지문 없이 풀리는 문항"을 검증 절차에 넣을 것인가.** SKILL.md "하지 않는 것"에는 있지만 4단계 재생성 조건은 키 불일치뿐이다. 01에서 6문항이 이 틈으로 통과했다.

## 남은 것

- format 모드 5장 중 3장 완료. 남은 2장의 입력은 준비됨: `04-B1B2-toeic-cloze-synonym-en.md`(토익형, (A)(B)(C)(D), 유의어 짝짓기), `pdf/05-A2-2col.pdf`(2단 편집 PDF, `extract.py` 2단 처리 후 첫 실제 호출. `extract-2col.md` 참고). 둘 다 아직 돌리지 않았다.
- 이번 실행은 장당 1회. pass^5는 측정하지 않았다.
- 사람 표본 채점, 내용 충실도 루브릭 채점은 하지 않았다.
- 원본 분석 JSON의 오답 이유와 단어집 예문은 에이전트가 쓴 것이다. `eval/sources/NN.expected.json`의 초안으로 쓸 때 이 필드는 걸러야 한다.
